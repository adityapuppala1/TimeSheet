# Whole-application audit — 2026-10-02

> **Audience:** the product owner, engineers and security reviewers · **Type:** explanation + record ·
> [Documentation index](README.md)

On 2026-10-02 the product owner asked whether any workflow was broken anywhere, whether the product
— from the login page through the platform-admin console — met industry standards, how the recent
Google and Microsoft sign-in changes affect organizations that already use them, and whether the
analytics were right and shown the right way. This document records what was found, what was
decided and why, what was fixed, and what is proposed next. The fixes themselves are in
[CHANGELOG.md](../CHANGELOG.md) (Unreleased); the endpoint and schema details are in
[API.md](API.md) and [DATABASE.md](DATABASE.md#audit-fixes-2026-10-02).

## How it was done

Nine read-only audits, each tracing its area end to end in the code and confirming the risky paths
with throwaway tests against the real controllers: signup/trials/billing/scheduled jobs, timesheets,
notifications and reports, tenant authentication, single sign-on, the platform console, tickets,
change management and users/roles, and analytics. About 130 findings came back, each graded by what
a person using the product would actually get. Every Critical and High was re-verified before it was
fixed; nine sub-audits found no claim that did not hold.

Fixes were made test-first — a test that reproduces the defect, seen failing, then the fix — in ten
parallel lanes, each in its own git worktree, merged one by one and re-checked as a whole: the lint
gate (warnings went down, never up), all API and web unit tests, and the end-to-end suite.

Then four fresh reviewers, who had written none of it, read the merged branch for what the fixes had
**broken or left** — regressions, merge interactions between lanes, edge cases on existing customers'
data. They found no Critical problems and fourteen Important ones (for example: SCIM could
deprovision a workspace's last super admin with no way back; extending a lapsed trial skipped every
retention notice before deletion; the top of a reporting tree could get no timesheet approved; a
stranger could keep the console owner locked out; a working SAML setup would have matched people by
a different address). Every Important finding was fixed the same way — test first — in a second set
of lanes, and the whole branch re-checked again.

## The short answer

| Area | Verdict before | Now |
|---|---|---|
| **Workflows** | Several genuinely broken: a lapsed workspace could not pay; console plan changes did not end trials; paying after suspension did not restore; every scheduled job ran once per API replica; an admin could take over a super admin. | Fixed — see below and the changelog. |
| **Login and sessions** | Sound core (rotating httpOnly refresh cookies, reuse detection, constant-time login). Gaps: a reset-link CPU denial of service, unthrottled forgot-password, silent sign-out failure, a lockout that reset itself, admin-set passwords never enforced. | Fixed. Tenant MFA is the main remaining gap (proposal 1). |
| **Single sign-on** | Google correct; Microsoft with no directory ID accepted any organization; SAML refused Entra's and Google's default signing and failed on multiple replicas; SSO from a custom domain started the wrong workspace; accounts created for anyone the IdP accepted. | Fixed in stages that lock nobody out. Identity binding by `tid`/`oid` is next (proposal 2). |
| **Platform console** | Good governance design, but a public owner password on fresh installs, single-person bypasses of two-person rules, a file-read path, and a console that could not finish creating an operator. | Fixed. |
| **Change management** | The plan could be edited while it waited for approval; a workflow that submitted a change opened no approval round; moving a change's ticket from the Tickets page bypassed the change. | Fixed: the plan locks at submission, every move goes through one service, the ticket follows its change. |
| **Tickets** | API, assistant and scanner moves skipped notifications, gates and audit; a reopen kept a breached SLA clock; intake tickets could not be triaged by the managers asked to; email replies opened duplicate tickets. | Fixed: one transition path for every surface, a fresh SLA clock on reopen, threaded email. |
| **Timesheets** | Anyone could approve their own hours; the approvals queue hid older entries; bulk reject told nobody; "today" was UTC's. | Fixed, with care for the top of the reporting tree and one-person workspaces. |
| **Analytics** | Mostly the right shape, often the wrong number: a manager's home page showed the whole workspace's hours as theirs; utilisation divided by future days; currencies were added together; failures showed as zero; console churn missed cancellations. | Fixed against written definitions (below). |

## Decisions, and the standard behind each

Where the code had to choose, it followed the published guidance below; where guidance and
"don't break working customers" pulled apart, the change was **staged** rather than switched on.

| Decision | Why | Source |
|---|---|---|
| Scheduled jobs run once per deployment through a database claim per tick, not "set replicas to 1" | Keeps HA for web traffic; the Helm autoscaler silently overrode the replica pin | — (house pattern, `PlatformJobClaim`) |
| A lapsed workspace pays from a dedicated page, without entering the app | The app's own background calls were what blocked payment | Atlassian / Slack lapsed-billing pages |
| Reset links are `selector.verifier`, looked up by index | One lookup and one compare per attempt; tokens are high-entropy so a fast hash is correct | OWASP Forgot Password Cheat Sheet; ASVS 5.0 §6.3 |
| Forgot-password answers first and caps mail per address | Response time must not reveal whether an account exists; mail bombing | OWASP Forgot Password Cheat Sheet |
| Admin-set passwords must be changed before anything else; admin-typed ones meet the policy | Initial passwords expire on first use; a guessable temporary one is an open door | ASVS 5.0 §6.4.1 |
| Password minimum stays 8, plus a common-password blocklist and a 72-byte cap | ASVS L1 floor; NIST asks for 15 only when the password is the sole factor — raise it with MFA | NIST SP 800-63B-4 §3.1.1.2; ASVS 5.0 §6.2 |
| Lockout escalates 5 → 15 → 60 minutes and stops there; a reset lifts it | Every extra hour is time a stranger can take from the owner; NIST allows ≤100 failures | OWASP Authentication Cheat Sheet; NIST 800-63B-4 §3.2.2 |
| "Remember me" off by default; unticked = browser-session cookie; idle timeout opt-in | Persistent sessions should be a choice | OWASP Session Management Cheat Sheet; ASVS 5.0 §7.3 |
| A workspace page may only make credentialed calls to its own host | Sibling subdomains are "same-site", so SameSite does not separate tenants | ASVS 5.0 §3.4 |
| Microsoft with no directory ID: refuse new ones, record who signs in from where, offer "Restrict to my directory" — never auto-lock | Token issuer comes from the token's own `tid`, so any directory passes; but switching it off would lock out working customers | MSRC "nOAuth" (2023); Microsoft claims-validation guidance |
| Automatic SSO account creation gets a switch and an allowed-domain list, default unchanged | Unrestricted JIT lets anyone the IdP accepts in; changing the default would surprise existing orgs | Slack, Atlassian Guard, Notion (JIT tied to verified domains) |
| Google: `email_verified` required, and for an allowed-domain list the `hd` claim must match | Google is authoritative for an address only for gmail.com or with `hd` | Google OpenID Connect guide |
| SAML accepts a signed response **or** a signed assertion | Entra and Google sign only the assertion by default | Microsoft and Google SAML docs; OWASP SAML Cheat Sheet |
| New SAML checks (issuer, Destination, Recipient) enforced on new configurations, warned on proven ones | Admins registered the ACS on whatever host they were on | OWASP SAML Cheat Sheet |
| Console: no default password; mandatory MFA for owners and operators in production; 12 h / 30 min sessions | Default credentials are the top admin-console risk | CISA Secure-by-Design alert (2023); Okta mandatory admin MFA; ASVS L2 session limits |
| Loosening retention and reactivating an operator need a second owner | A single operator could otherwise delete workspaces without the two-person rule | NIST SP 800-53 AC-5 (separation of duties) |
| Rescue admin emails the customer's super admins | Support access to a customer account should be visible to the customer | Atlassian data-access requests; Salesforce "Grant Login Access" |
| Standard changes still need approval | Without a template catalogue, a self-chosen "pre-approved" type is a loophole | ServiceNow standard-change templates (ITIL) |
| A timesheet's author can't approve it, nor can someone the author manages | Segregation of duties | SOX-style SoD |

## Single sign-on: what changes for organizations already using it

Nothing below turns a working configuration off.

- **Google.** Unchanged for Workspace and verified consumer accounts. A Google account without a
  verified email is refused (since the earlier 🔐 change); the person now sees a readable reason on
  the sign-in page instead of JSON. New accounts are still created on first sign-in unless an admin
  switches that off or lists allowed domains — **recommended: list your company domains** (the card
  offers your claimed ones in one click), and set the OAuth client's audience to *Internal* in
  Google Cloud.
- **Microsoft with a Directory (tenant) ID.** Unchanged. The connection test now says "configuration
  looks valid" instead of "passed", because only a real sign-in proves the secret.
- **Microsoft without a Directory ID.** Still works for everyone — no token is refused. But it
  accepts accounts from **any** Entra directory and personal Microsoft accounts, matched by email.
  The settings card now shows which directories people actually sign in from and offers **Restrict to
  my directory**, listing exactly who that would shut out. **Recommended: do it.** New configurations
  require a Directory ID, and the platform console flags every workspace still open.
- **SAML.** Configurations that worked keep working (same entity ID and ACS). Entra and Google
  default-signing setups that were failing now work, and so does a deployment with several API
  servers. A configuration whose IdP sends only a transient or persistent NameID with no email
  attribute is now refused — map an email attribute.
- **LDAP.** Unchanged for single-match filters; a filter that matches two people for one address
  (which used to pick one at random) is now refused until it is narrowed.

## Analytics: how each number is now defined

The audit found the analytics mostly the right shape but often the wrong number: the same word
("hours", "open", "SLA", "converted") meant three to five different things across pages, "today" was
mostly UTC's, and a failed request rendered as a reassuring zero. The rules every metric now follows:
a number says what it measures, over which period and in which timezone (IST via `utils/platform-time.ts`);
no data is shown as "—" with a retry, never as 0; one definition per metric, in one place; people
counts exclude AI agent identities and deactivated users; money carries its currency from the data
and is never summed across currencies; numbers are formatted en-IN.

### Workspace metric definitions

- **Logged hours** — SUBMITTED + APPROVED, not deleted. Drafts and rejected hours appear only as their
  own labelled rows or as "not counted". **Approved hours** — APPROVED. The grouped timesheet report is a
  filterable listing and counts every status its filter allows; the analytics panel beside it says how
  many hours it left out.
- **Capacity** — working days from the window's start up to today (IST), minus booked time off, times
  the person's daily capacity. Target utilisation is shown beside it, not multiplied in.
  **Utilisation** = logged ÷ capacity for the same person; null without capacity.
- **Workforce** — active human employees and team leads, the same people on both sides of every
  figure; a share is null, not 0%, when there is nobody to measure.
- **People** — not deactivated, not deleted, not an AI agent identity.
- **Open ticket** — not RESOLVED or CLOSED. **Closed in a window** — resolved in it, or closed in it
  without ever being resolved.
- **SLA breached** — `(resolvedAt ?? now) > dueAt`; "breaches now" = open and past due. It never reads
  the sweep's `slaBreachAt`, so it works with the sweep off. **Overdue** — planned end before today
  (IST), or SLA breached. **Approval SLA** — `(reviewedAt ?? now) > approvalDeadline`.
- **Resolution time** — the median over tickets resolved in the last 28 days, against the 28 days
  before, null when empty, with the sample size shown. **First response** — the first comment by
  someone other than the reporter, an agent or a system account. **Reopen rate** — of tickets first
  resolved in the window, the share later reopened (never above 100%).
- **Weeks** start Monday 00:00 IST; **today** and **this month** are India's.
- **Comparisons** — the same weekdays, whole weeks earlier ("vs the same days last week"); a zero
  baseline reads "new"; a figure that describes "now" has no comparison at all.
- **Money** — each amount in its own currency; totals per currency, never added across currencies;
  burn % only over budgeted projects, in the budget's own currency.
- **Formatting** — en-IN (₹12,34,567; 12L / 1.2Cr), hours to one decimal, dates as "2 Oct 2026", and "—"
  for anything missing.

### Console metric definitions

These follow the SaaS-metrics conventions of ChartMogul and Stripe.

- **Paying customer** — ACTIVE, not trialing, on a paid tier, with list MRR not known to be zero. A tier
  with no list price (Enterprise) is paying with MRR unknown; never-measured seats are "unmeasured".
- **Free account** — ACTIVE, not trialing, on a tier listed at 0 (Starter). Reported separately, never a
  logo and never in a churn denominator.
- **List MRR** — over revenue-bearing accounts, list price × active non-agent seats; seats are carried
  forward over an unreachable night. ARR = MRR × 12; ARPA = MRR ÷ priced paying accounts.
- **Churn window** — start = paying customers on the window's FIRST snapshot day; churned = start
  customers not paying at the end, by any route (a cancellation to Starter is churn); new = paying at
  the end but not at the start. Logo churn = churned ÷ start; revenue churn = (churned + contraction) ÷
  start MRR; NRR = the start cohort's MRR at the end ÷ start MRR; GRR = (start − churned − contraction) ÷
  start MRR. Null when there is no start cohort.
- **Converted** — one rule (`services/trial-conversion.ts#isConverted`): no trial tier, or a Stripe
  subscription, or a paid plan. A conversion is dated (`Organization.convertedAt`) when it happens.
- **Trial → paid** — by the month the trial started (cohorts, latest 12); the headline covers trials
  started inside the selected window. Conversion = converted ÷ (converted + lapsed); median days to
  convert over dated conversions, with undated ones counted.
- **Billed MRR** — Stripe's recurring price for `active` and `past_due` subscriptions, net of `forever`
  and unexpired `repeating` coupons, per month; the gap to list price is "gap to list price".
- **Signup funnel** — distinct people (`emailHash`) whose first code fell in the period; each later step
  counts cohort people who verified, so no step exceeds 100%.
- **Needs attention** — a health band other than healthy, excluding deleted, archived and
  long-lapsed workspaces; an unreachable database reads "Workspace unreachable".
- **Open tickets** — OPEN, IN_PROGRESS, IN_REVIEW and REOPENED, excluding soft-deleted tickets.
- **Days, weeks, months** — India's: weeks run Monday to Sunday, months and the email chart's days are
  Indian calendar days, and today is included.

## Proposed next, in priority order

These were found, judged worth doing, and deliberately not built in this pass — each needs a product
decision, a migration with a rollout, or more than a day's work. Design sketches are in the lane
reports summarised here.

1. **Tenant MFA (TOTP + recovery codes, then passkeys)** with a workspace policy (off / super admins /
   everyone), and step-up re-authentication for SSO, role, API-key and security settings. The biggest
   remaining standards gap (ASVS 5.0 L2 §6.3.3, NIST AAL2). Reuse the console's TOTP code.
2. **SSO identity binding** — a `UserIdentity` table keyed on (provider, issuer/`tid`, `sub`/`oid`):
   bind on next sign-in, refuse a different subject with the same email afterwards, then auto-pin a
   Microsoft configuration that has only ever seen one directory. Closes nOAuth for good (OIDC Core
   §5.7: email "MUST NOT be used as unique identifiers").
3. **Browser-bound OIDC state** — route `/start` through the callback host to set an httpOnly cookie
   holding the PKCE verifier and a nonce, and check the ID token's `nonce` (RFC 9700 §2.1).
4. **A shared store for lockout and rate limits** (control plane or Redis), weighted by (account, IP),
   so limits hold across replicas and are harder to use against a victim.
5. **Console step-up and customer-granted support access** — re-authenticate before approve, download
   and rescue; let a workspace grant platform support a time-boxed access window, mirrored into its
   own audit log.
6. **A tamper-evident platform audit log** — hash chain plus optional streaming to a SIEM, and audit
   of console sign-ins.
7. **LDAP StartTLS and a custom CA**, required for new configurations (RFC 4513); **SSO certificate
   and secret expiry alerts** at 30/7/1 days; **break-glass recovery codes** for SSO-only workspaces.
8. **Temporary-password expiry** (72 h) and a **higher minimum length** once MFA ships.
9. **Per-purpose keys** derived from one secret with HKDF instead of one secret for nine uses.

## Upgrade notes for operators

- **Scheduled reports.** Deliveries owned by a manager or team lead that go to any address outside
  the workspace are **paused** by the upgrade (they now cover the same projects as the live dashboard,
  which includes the owner's team's). The owner sees why and can **Resume** after checking the
  recipients.
- **Approval-request emails** to timesheet approvers now have their own template and follow the
  "Approval SLA breached" email toggle rather than "Submission confirmation".
- **Request forms** that were set to the CHANGE ticket type are moved to BUG.
- **A queued retention-policy request** raised before the upgrade must be raised again (approvals now
  apply only the changes they show).
- **Console signing secret.** With `NODE_ENV=production` the API now refuses to boot when
  `PLATFORM_ADMIN_JWT_SECRET` is weak, a placeholder, or the same as `JWT_ACCESS_SECRET` or
  `JWT_REFRESH_SECRET`. Generate a fresh one (`openssl rand -base64 48`) **before** upgrading.
- **Console password.** Fresh installs print a generated password once. Existing installs keep
  theirs; one still on the public dev value keeps its banner. In production, owners and operators
  without MFA are sent to enrolment at their next sign-in.
- **Console sessions** now last 12 hours and end after 30 idle minutes.
- **Snapshots.** Pre-deletion snapshot folders must sit inside `SNAPSHOT_ROOT`; one configured
  elsewhere stops being listed until it is moved inside.
- **Scheduled jobs** no longer need `api.replicaCount: 1`.
- **A workspace the old code suspended after a failed renewal** and that has since paid needs
  restoring by hand once: `status = 'SUSPENDED' AND suspendedReason = 'A renewal payment failed.'`,
  then check its Stripe subscription.
- **Users who were created or reset by an admin** and never changed that password will be asked to at
  their next password sign-in.
- **Workspace migrations:** run `npm run db:migrate:tenants` after deploying, as for every release.
