The headline: measure, then cut

The ticket list shipped 391 KB of JSON per request while the database contributed only 25 ms — the endpoint was serializing rich-text prose nothing in the list renders. Dropping description from the list (the detail view fetches its own) cut the payload to 150 KB (gzip: 46→10 KB) and moved the same load test from 129→163 req/s, p50 383→304 ms — with zero client changes, because the client's own types never declared the field.

Every ceiling got a knob

Load testing found three fixed limits and made each an operator decision: the blanket per-IP limiter (RATE_LIMIT_PER_MINUTE — one office NAT was one 900/min bucket), the per-tenant DB pool (TENANT_DB_CONNECTION_LIMIT — 5 connections is multi-tenant math; single-org shapes now ship 20), and Kubernetes CPU limits (chart values). All three flow through Compose, the Helm chart, and .env.example, defaults unchanged.

Method

autocannon (Node) against each stack in sequence, whole machine per run: 16-core Windows host. Scenarios: unauthenticated /api/health, authenticated GET /api/tickets (heaviest common read), and a capped 300-request login flood (bcrypt cost). Rate limiter raised via the new knob for capacity runs — the limiter itself was validated first (exactly 200,000 requests passed at a 200k/min setting, then 429s). Honesty notes: Compose/Kubernetes run inside Docker Desktop's VM (network tax measured on health: ~7×); k8s calls traverse kubectl port-forward; container-stack ticket lists were empty (fresh seed), so cross-stack ticket numbers are floors of the authed path, not payload tests; all connections shared one session token — real users don't, so single-session contention overstates the plateau (distinct-token rerun listed under Next steps).

Why logins are the spike to plan for

Password hashing costs ~240 ms of CPU per login by design — that is the bcrypt work factor doing its job against offline cracking. One process sustains ~4 logins/s; a hundred people at 9 am is ~25 s of queued CPU on one pod, or a non-event across an HPA fleet that scales on exactly this signal. SSO deployments sidestep it entirely.
